## Главные правила (ADR)

### ADR-001: Ядро = сайт, интерфейсы = тонкие клиенты
Вся новая бизнес-логика в перспективе живёт в `baza_znanii` и отдаётся через API.
Admin_PC и бот — только интерфейсы. Конечная цель: онлайн-админка в `/admin` сайта.

### ADR-002: Новые админ-функции — только в Admin_PC
Бот `Admin_moi_class` заморожен: только багфиксы, новых функций не добавлять.
Причина: Admin_PC удобнее, функции уже дублируются, двойную работу прекращаем.

### ADR-003: Модули Admin_PC — будущие модули сайта
`mk_api.py`, `report_builder.py`, `topic_planner.py`, `workoff.py`, `transfer.py`, `pdf_generator.py`
писать так, чтобы перенос в `baza_znanii/app/` был копированием: без жёстких путей Windows
(выносить в config), без глобального состояния, логика — в модулях, не в роутерах.

### ADR-004: Данные тем уроков — источник один
Сейчас: сайт/vault → `build_report_sources.py` (в боте) → `report_sources.json` → читают бот и Admin_PC.
План: разместить темы всех направлений на сайте и отдавать их API'ем; `report_sources.json` отомрёт.
Пока: источник обновляется только через `Admin_moi_class/ОБНОВИТЬ_ИСТОЧНИКИ.bat`.

### ADR-005: Внутри baza_znanii — два продукта, разделены роутерами
- Портал преподавателя: `main.py`, `agent.py`, `vault_fs.py`, шаблоны не-student.
- Онлайн-уроки ученика: `student.py`, `student_agent.py`, `student_fs.py`, шаблоны `student_*`.
Импортов между ними быть не должно — только через общее ядро (`auth.py`, `deps.py`, `main.py`).

## Общие правила разработки (действуют во ВСЕХ проектах)

Внедрены 2026-10-27 по плану «практики вайб-кодинга» (`baza_znanii/docs/vibe_coding_plan.md`, приоритеты ①–④). Проектные AGENTS.md не дублируют их, а ссылаются сюда.

1. **Тесты — критерий сдачи фичи.** Каждая новая фича/фикс → тест(-ы) в `tests/` проекта (unit/API, без сети; негативные сценарии обязательны). Перед сдачей прогонять ВЕСЬ набор (прогон одной командой — `run_tests.bat` или `tests/run_all.py` проекта). Красное = чинить; не получается — сигналить пользователю, не сдавать молча. Удалять/ослаблять чужие проверки нельзя без явного решения пользователя.
2. **status.md ≠ history.md.** `status.md` — только актуальное состояние и планы (коротко). `history.md` — append-only дневник: новые записи сверху, по одной на сессию, старые не редактировать. Дневниковые записи в status.md не писать.
3. **Документация после каждой фичи — обязательный шаг.** После реализации и зелёных тестов обновить: status.md (актуальное), history.md (запись), AGENTS.md проекта (если изменилась структура/правила).
4. **Факты, проверяемые машиной, в status.md не писать** (состояние деплоя, версии и т.п. — только решения, планы, причины).
